# Prompt History Record: Phase V Cloud Native Todo Spec

## Summary
Created the feature specification for Phase V of the Todo Evolution project, transforming it into an event-driven, cloud-native distributed system with advanced task intelligence and Kubernetes deployment.

## Original Prompt
```
# speckit.specify
## Project: Evolution of Todo – Phase V (Advanced Cloud-Native AI System)

---

## 1. Phase Objective

Evolve the existing Todo AI Chatbot into a **fully event-driven, cloud-native, production-grade distributed system** by adding advanced task intelligence, asynchronous processing, and cloud deployment.

This phase builds on Phase IV and MUST NOT break any existing functionality.

---

## 2. In-Scope Capabilities (WHAT must exist)

### 2.1 Advanced Todo Features

#### 2.1.1 Due Dates & Reminders
- Users can assign a due date and time to a task using natural language.
- Users can request reminders (e.g., "Remind me 1 hour before").
- Reminder delivery must be asynchronous and event-driven.
- Reminder scheduling must survive pod restarts and redeployments.

**Examples**
- "Remind me tomorrow at 9am to submit the report"
- "Set a reminder 30 minutes before the meeting task"

---

#### 2.1.2 Recurring Tasks
- Users can create tasks that repeat:
  - Daily
  - Weekly
  - Monthly
- Completing a recurring task automatically creates the next occurrence.
- Recurrence logic must not run inside the Chat API service.

**Examples**
- "Pay rent every month"
- "Weekly team sync every Monday"

---

#### 2.1.3 Priorities
- Tasks support priority levels:
  - High
  - Medium
  - Low
- Priority can be set and changed via natural language.

**Examples**
- "Mark groceries as high priority"
- "Show me low priority tasks"

---

#### 2.1.4 Tags / Categories
- Tasks can have one or more tags.
- Tags are user-defined and searchable.

**Examples**
- "Add tag work to the presentation task"
- "Show me home tasks"

---

#### 2.1.5 Search, Filter & Sort
- Users can:
  - Search tasks by keyword
  - Filter by status, priority, tag, or due date
  - Sort by due date, priority, or creation time

**Examples**
- "Show pending high priority tasks"
- "Sort my tasks by due date"

---

## 3. Event-Driven Behavior (WHAT events must happen)

### 3.1 Task Lifecycle Events
Every task operation MUST emit a domain event:
- task.created
- task.updated
- task.completed
- task.deleted

Each event MUST contain:
- task_id
- user_id
- full task snapshot
- timestamp

---

### 3.2 Reminder Events
- Creating or updating a task with a due date MUST schedule a reminder event.
- Reminder events MUST be emitted at the exact scheduled time.

---

### 3.3 Recurring Task Events
- Completing a recurring task MUST emit an event.
- A new task instance MUST be created asynchronously in response.

---

## 4. Services (WHAT must exist)

### 4.1 Chat API Service
- Handles:
  - User conversations
  - Natural language understanding
  - MCP tool invocation
- MUST remain stateless.
- MUST NOT contain:
  - Reminder logic
  - Recurrence logic
  - Kafka client code

---

### 4.2 Recurring Task Service
- Consumes task completion events.
- Creates next task instances for recurring tasks.
- Operates independently from Chat API.

---

### 4.3 Notification Service
- Consumes reminder events.
- Sends user notifications (log-based or mock delivery is acceptable).

---

### 4.4 Audit / Activity Service
- Consumes all task lifecycle events.
- Stores immutable activity history.

---

## 5. Dapr Requirements (WHAT capabilities must be used)

- Pub/Sub for all events
- State Store for conversation or task-related state
- Jobs API (or equivalent) for exact-time reminders
- Service Invocation for inter-service calls
- Secrets management for credentials

---

## 6. Deployment Requirements

### 6.1 Local Deployment
- System MUST run on Minikube.
- All services deployed via Helm charts.
- Dapr sidecars enabled for all backend services.

---

### 6.2 Cloud Deployment
- System MUST deploy to a managed Kubernetes service:
  - AKS or
  - GKE or
  - OKE
- CI/CD pipeline MUST deploy automatically from GitHub.

---

## 7. Non-Functional Requirements

### 7.1 Scalability
- Services MUST scale horizontally.
- No single service may become a bottleneck.

---

### 7.2 Resilience
- System MUST tolerate:
  - Pod restarts
  - Event replays
  - Partial failures

---

### 7.3 Backward Compatibility
- Phase III and IV functionality MUST continue to work without changes to user behavior.

---

## 8. Acceptance Criteria (Phase V is DONE when)

- Advanced task features work via chatbot
- Events flow through Kafka using Dapr
- Reminder & recurring logic works asynchronously
- System runs on Minikube and cloud Kubernetes
- No manual code or infra changes exist
- All implementations trace back to specs and tasks

---

## 9. Out of Scope

- Mobile apps
- Paid notification services
- Multi-tenant org features
- AI fine-tuning

---

## 10. Constraints

- No manual coding
- No direct Kafka client usage
- No stateful backend services
- Spec-Kit Plus workflow is mandatory
```
